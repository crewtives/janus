# Wiki-links broken by race condition when dates within a project run in parallel

## Problem
The initial pipeline design used a flat `p-queue` that dispatched individual `(project, date)` tasks with `concurrency: 2`. Two tasks for the same project at adjacent dates ran concurrently. Day N's pulse generation looks for day N-1's file on disk to populate `[[Pulse anterior: YYYY-MM-DD-<project>]]`. When N-1 was still being generated by the parallel worker, N saw nothing and either skipped the back-link or pointed two days back, producing broken wiki-links in the Obsidian graph.

## Symptoms
- After a 7d backfill across 7 projects: 23 out of 43 expected `Pulse anterior` wiki-links resolved to non-existent files
- Pulses appear isolated in Obsidian's local graph (`Ctrl+G` on a project hub)
- `bun janus pulse --backfill 7d` reports all-OK; the corruption is in the cross-references, not the file count
- Re-running pulse with `--force` doesn't help; the race recurs

## What Didn't Work
- Increasing the wait between p-queue tasks (`intervalMs`) — only widens the race window, doesn't close it
- Reading the previous pulse from the state DB instead of disk — same race, the DB row is written by another task in parallel
- A retry-with-feedback that re-reads the previous pulse — works for individual cases but is not a structural fix; first runs still produce broken links

## Solution
Serialize dates within each project. Each project becomes ONE p-queue task that loops through its dates serially. The global `concurrency: 2` now parallelizes **projects**, not date tasks. From `src/pipeline/orchestrator.ts:93-148`:

```ts
// Serialize per project: each project is enqueued as ONE task that
// processes its dates in ascending chronological order. p-queue runs N
// projects in parallel (global concurrency), but within a single project
// dates run serially — guaranteeing that when day N is processed, day
// N-1's pulse is already written to disk, and the
// `Pulse anterior: [[YYYY-MM-DD-<project>]]` wiki-links point to the
// immediately previous one without race conditions.
for (const project of projects) {
  // ...
  queue.add(async () => {
    pendingDates.sort();  // ascending: day N depends on day N-1
    for (const date of pendingDates) {
      // ... process date serially
    }
  });
}
```

The fix is pinned by `tests/orchestrator-serial.test.ts`.

`src/core/previous-pulses.ts` reads `immediatePrevious` from disk (filesystem readdir + filter), so once the prior day's file exists, the next day's prompt can reference it correctly.

## Why This Works
The race was structural — concurrent producers writing files that other concurrent producers read. Serializing per-project removes the producer/consumer overlap within a project while keeping cross-project parallelism for throughput. The orchestrator's `pendingDates.sort()` ensures ascending order so day N always sees day N-1 already written.

## Prevention
- `tests/orchestrator-serial.test.ts` asserts the invariant — do not delete or weaken
- The comment block at `src/pipeline/orchestrator.ts:93-99` documents the rationale; do not refactor the loop into per-date enqueues without re-deriving why
- Any new artifact that cross-references the previous day (weekly cross-pulse links, spine continuity sections) must respect the same invariant — within a project, generate in date order
